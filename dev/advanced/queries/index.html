    Structured and CTS queries¶

    Choose a query vocabulary, then use the same API to serialize and search:

    Structured queries CTS queries
    Builder sq from mlclient.search cts from mlclient.xquery
    Native format Search API structured JSON/XML CTS JSON/XML
    Local serialization serialize(), to_json(), to_xml() serialize(), to_json(), to_xml()
    Combined query to_combined_query() under query to_combined_query() under ctsquery
    REST execution ml.search ml.search
    XQuery compilation and execution Not supported compile(), ml.eval.expression(), CtsService

    Shared serialization API¶

    Both families implement QueryComponent and SearchQuery. The API is shared; their native wire formats remain distinct. Build equivalent queries with either vocabulary:

    from xml.etree.ElementTree import tostring

from mlclient.search import sq
from mlclient.xquery import cts

structured_query = sq.query(sq.and_(sq.collection("reports"), sq.term("blue")))
cts_query = cts.and_query(
    [
        cts.collection_query("reports"),
        cts.word_query("blue"),
    ]
)

for query in (structured_query, cts_query):
    json_query = query.serialize()  # Same as serialize("json") or to_json().
    xml_query = query.serialize("xml")  # Same as to_xml(); an ElementTree element.
    xml_text = tostring(xml_query, encoding="unicode")
    combined = query.to_combined_query()

    Use to_json() when you need a Python dictionary, or to_xml() when you need an ElementTree element. MLClient builds either representation locally from the query object, without making a server request. Each call returns a new result, so you can modify it without changing the query. Optional settings set to None are omitted; explicit False and 0 values are retained.

    Execute over REST¶

    ml.search accepts both query families and serializes them locally:

    from mlclient import MLClient

with MLClient() as ml:
    structured_documents = ml.search.documents(structured_query)
    cts_documents = ml.search.documents(cts_query)

    Native JSON or Python query objects¶

    ml.search accepts structured, CTS and combined JSON dictionaries as well as our Python query objects. Keep the native root member: query for structured JSON, ctsquery for CTS JSON, or search for a combined query. The service wraps standalone structured or CTS JSON in a combined request and applies the same service and operation scopes as for Python objects.

    with MLClient() as ml:
    structured_documents = ml.search.documents(
        {
            "query": {"term-query": {"text": "coffee"}},
        }
    )
    cts_documents = ml.search.documents(
        {
            "ctsquery": {"wordQuery": {"text": "coffee"}},
        }
    )

    Use sq or cts when you want Python constructors and local validation; use dictionaries when you already have native JSON. Both are sent as application/json. Strings remain Search API text queries, not JSON or XML source. See the lexicon restriction below for raw CTS JSON.

    Combined queries with options and text¶

    Both structured and CTS queries accept options= and qtext= in to_combined_query(). Options are inline members as a dictionary, without an outer options wrapper, or a SearchOptions composition built with opt. qtext is an additional Search API string query; MarkLogic ANDs it with the structured or CTS query.

    from mlclient.search import opt, sq

options = opt.options(opt.word_constraint("title", sq.element("title")))
combined = sq.collection("reports").to_combined_query(
    options=options,
    qtext="title:coffee",
)

with MLClient() as ml:
    documents = ml.search.documents(combined)

    to_combined_query(options=..., qtext=...) accepts an inline options dictionary or a SearchOptions object, including the result of opt.options(...), for both structured and CTS queries. It returns a fresh {"search": {...}} dictionary. Structured queries go under query (wrapped in Query when needed), CTS queries under ctsquery, and options and qtext alongside them inside search. Mutating the result does not change the query or supplied options. Omitted or None settings are left out; explicit empty dictionaries and empty strings are retained.

    ml.search accepts this JSON combined query directly. Inline scope options supply defaults; options in the combined query override matching members, and options in the operation's scope=SearchScope(...) override both. Each option member is replaced as a whole, including lists of constraints. An operation scope with options=None clears all inline and installed options. An installed options name replaces the selected name and travels in the URL; MarkLogic merges its server-side definitions with the combined query's inline options. Naming installed options does not replace inline members locally.

    For lower-level requests, pass the same dictionary as the body of ml.rest.search.post() or ml.rest.values.post().

    For lexicon operations (values, tuples, aggregate), raw CTS JSON, standalone or inside a combined query, is rejected: /v1/values ignores that filter. Pass a CTS query object with service options instead, so the service can send the required additional-query XML. Combined structured queries work on both search and lexicon endpoints.

    Structured queries¶

    Build Search API queries with sq or classes from mlclient.search.structured. Wrap subqueries in Query when passing them directly to the Search API.

    Builder¶

    The sq module provides short constructor aliases and composition functions. Names that conflict with Python keywords or builtins have a trailing underscore: and_, or_, not_, and range_. Query classes retain their full names, such as AndQuery and RangeQuery.

    from mlclient.search import sq

query = sq.query(
    sq.and_(
        sq.range_(sq.element("price"), 20, operator="GE", index_type="xs:int"),
        sq.term("blue"),
    )
)
json_query = query.serialize()
xml_query = query.serialize("xml")

    Import it with from mlclient.search import sq, or import an individual function with from mlclient.search.sq import term. Leaf factories accept the same parameters as the corresponding classes because they are aliases of those constructors; composition functions query, and_, or_, and near accept positional subqueries.

    Structured serialization details¶

    A query validates its arguments when it is built, so an invalid selector, operator, fragment scope or value cardinality raises ValueError or TypeError at construction, not later inside a search. Queries are immutable and hashable: list arguments are stored as tuples, so AndQuery([q]) equals AndQuery((q,)).

    Both representations retain literal values, repeated criteria, target namespaces, explicit zero and false options. JSON uses the Search API's native cardinality and metadata representation, not the native CTS JSON grammar. Numeric options, including geographic coordinates, distances and weights, must be finite in both formats; range and value query values may be INF, -INF or NaN and remain lexical text with their declared index type.

    The model classes can also be constructed directly:

    from xml.etree.ElementTree import tostring

from mlclient.search.structured import (
    AndQuery,
    CollectionQuery,
    Element,
    Query,
    WordQuery,
)

query = Query(
    AndQuery(
        [
            CollectionQuery("reports"),
            WordQuery(Element("title"), "annual", options=["case-insensitive"]),
        ]
    )
)
xml = tostring(query.serialize("xml"), encoding="unicode")

    Query values are XML text, not executable code. ElementTree escapes text and attribute values during serialization. Namespace prefixes in the output do not affect the query's meaning; the namespace URI identifies the Search API elements.

    XML and JSON document targets¶

    Use Element for XML elements, optionally with an Attribute selector; JsonProperty for JSON properties; or Field for configured database fields. The query's XML format does not restrict it to XML documents. Do not mix target kinds in one query.

    from mlclient.search import sq

xml_value = sq.value(sq.element("item"), "published", attribute=sq.attribute("status"))
json_number = sq.value(sq.json_property("count"), 7, node_type="number")
json_boolean = sq.value(sq.json_property("active"), True, node_type="boolean")
json_null = sq.value(sq.json_property("deleted"), "", node_type="null")

    JSON value queries default to string matching on the server. Set node_type explicitly for numbers, booleans, or null values. Word queries only match text.

    sq.range_ uses the same selectors, with a comparison operator and index type. Pass sq.path_index(...) as its target for a path range index:

    from mlclient.search import sq

price = sq.range_(sq.element("price"), 20, operator="GE", index_type="xs:decimal")
path = sq.range_(
    sq.path_index(
        "/r:report/r:price", namespaces={"r": "https://example.com/example/reports"}
    ),
    20,
    operator="GE",
    index_type="xs:decimal",
)

    The index must already exist in the database. Local serialization validates the Python arguments; MarkLogic checks database configuration when executing the query. See the native structured-query reference for index requirements and query semantics.

    Search options¶

    Build options by nesting immutable components, just as sq composes query objects. The opt module provides factories using the signatures of their corresponding classes. For example, opt.word_constraint(...) constructs a WordConstraint, and opt.options(...) constructs SearchOptions. Use Range or opt.range_(...) for an index target.

    Selectors such as sq.element, sq.json_property and sq.field also describe targets in search options. Although they come from the structured-query namespace, options built with them work with structured queries, CTS queries and text queries alike. For example, a CTS collection filter can be combined with a text constraint whose target is defined by sq.element():

    from mlclient import MLClient
from mlclient.search import opt, sq
from mlclient.xquery import cts

options = opt.options(opt.word_constraint("title", sq.element("title")))
combined = cts.collection_query("reports").to_combined_query(
    options=options,
    qtext="title:coffee",
)

with MLClient() as ml:
    documents = ml.search.documents(combined)

    CTS index references and CTS query constructors are not option target selectors; use sq selectors or their corresponding classes when defining these options.

    from mlclient.search import opt, sq

base = opt.options(
    opt.word_constraint("title", sq.element("title")),
    opt.page_length(10),
)
custom = opt.options(base, opt.page_length(20), opt.return_facets(False))

# base still requests 10 results; custom requests 20.
with MLClient() as ml:
    documents = ml.search(options=custom).documents("title:coffee")

    Each group keeps its components in order. Repeatable options, such as constraints, values, tuples and sort keys, accumulate. A later non-repeatable option, such as page length, replaces an earlier one. Neither composition nor serialization changes the original group. JSON and XML are built independently and returned as fresh representations.

    The class API is equivalent and has the same typed parameters:

    from mlclient.search.options import PageLength, SearchOptions, WordConstraint
from mlclient.search.structured import Element

options = SearchOptions(
    WordConstraint("title", Element("title")),
    PageLength(20),
)

    Use named constraints in a query¶

    A constraint query names a definition from the options. Define the target with opt, refer to its name with sq, and pass both to the search service:

    from mlclient import MLClient
from mlclient.search import opt, sq

options = opt.options(
    opt.range_constraint(
        "price",
        opt.range_(sq.element("price"), "xs:decimal"),
        facet=False,
    ),
    opt.word_constraint("title", sq.element("title")),
)
query = sq.query(
    sq.and_(
        sq.range_constraint("price", 20, operator="GE"),
        sq.word_constraint("title", "blue"),
    ),
)

with MLClient() as ml:
    documents = ml.search(options=options).documents(query)

    The query constructors validate their arguments, including a non-empty constraint name; they do not resolve the corresponding options definition. For JSON value constraints, set node_type on opt.value_constraint(...), just as you do on sq.value(...) for an inline value query.

    Typed options and nested components¶

    opt covers the Search API options vocabulary, including nested definitions. Every constructor is an alias of the corresponding class in mlclient.search.options.

    Configure Constructors
    Paging, scoring and execution page_length, quality_weight, concurrency_level, forest, fragment_scope, search_option, debug
    Search report members return_aggregates, return_constraints, return_facets, return_frequencies, return_metrics, return_plan, return_qtext, return_query, return_results, return_similar, return_values
    Named constraints range_constraint, word_constraint, value_constraint, collection_constraint, container_constraint, properties_constraint, geo_constraint, custom_constraint
    Facet intervals bucket, computed_bucket; pass them to range_
    Geospatial indexes geo_element, geo_element_pair, geo_attribute_pair, geo_json_property, geo_json_property_pair, geo_path, geo_region_path; pass an index to geo_constraint, values or tuples
    Lexicons and aggregates values, tuples, aggregate, collection
    Suggestions and unqualified terms suggestion_source, default_suggestion_source, word_lexicon, word, value, term, term_default
    Query grammar and named states grammar, implicit, starter, joiner, operator, operator_state
    Results and metadata sort, transform_results, preferred_matches, extract_document_data, extract_metadata, metadata_qname, constraint_value, result_decorator, annotation
    Additional filtering and extensions additional_query, callback, anchor

    For example, define price bands and choose what the search report returns:

    from mlclient.search import opt, sq

options = opt.options(
    opt.range_constraint(
        "price",
        opt.range_(
            sq.element("price"),
            "xs:decimal",
            buckets=[
                opt.bucket("budget", "Under 20", lt="20"),
                opt.bucket("premium", "20 and above", ge="20"),
            ],
        ),
    ),
    opt.transform_results(
        preferred_matches=opt.preferred_matches([sq.element("title")]),
        max_matches=2,
    ),
    opt.return_metrics(False),
    opt.quality_weight(0.5),
)

with MLClient() as ml:
    report = ml.search(options=options).report("coffee")

    The range index must already exist. range_ also accepts fragment_scope, weight, options (range options), facet_options and computed_buckets. Word and value constraints accept fragment_scope, weight and an optional annotation. sort accepts a range index or a native marker such as "score", "document-order" or "unordered".

    Reuse a geospatial index definition in a named constraint:

    location = opt.geo_element(
    sq.element("location"),
    sq.element("point"),
    options="coordinate-system=wgs84",
    heatmap=opt.heatmap(-90, -180, 90, 180, 18, 36),
)
options = opt.options(opt.geo_constraint("location", location))

    Geo constructors take sq selectors, like range_. A selector can also be a sequence when the native definition names several elements, properties or paths. Region-path indexes do not support heatmaps or facet options.

    values and tuples accept style, options (values options), aggregates and annotation. Tuples preserve index order, including mixed index kinds:

    options = opt.options(
    opt.tuples(
        "uri-price",
        "uri",
        opt.range_(sq.element("price"), "xs:decimal"),
        aggregates=[opt.aggregate("count")],
    ),
)

    Choose term matching or suggestions by nesting their source definitions:

    options = opt.options(
    opt.term(
        opt.term_default(opt.word(sq.element("title"))),
        empty="no-results",
        options="case-insensitive",
    ),
    opt.default_suggestion_source(
        opt.word_lexicon("http://marklogic.com/collation/"),
        options="limit=5",
    ),
)

    For custom parsing, faceting or result decoration, callback identifies the function by apply, ns and at; the module must already be installed. operator_state takes an opt.options(...) group containing the options allowed in a state. Use opt.options(..., namespaces={...}) for prefix bindings needed by grammar QNames or custom extension data.

    additional_query accepts a CTS query object. MarkLogic's options JSON requires its CTS query as a quoted XML string; this constructor supplies that form. The same native requirement applies to implicit in a grammar.

    XML-only range settings and legacy options¶

    MarkLogic 10 and 12 do not preserve range nullable or custom anchor elements when converting JSON options to XML. These settings are available through range_(..., nullable=True) and range_(..., anchors=[opt.anchor(...)]), but to_json() raises TypeError. Send their XML form through the raw REST API:

    from xml.etree.ElementTree import Element, tostring

from mlclient.search.structured import SEARCH_NS_URI

options = opt.options(
    opt.values("price", opt.range_(sq.element("price"), "xs:decimal", nullable=True)),
)
body = Element(f"{{{SEARCH_NS_URI}}}search")
body.append(options.to_xml())
with MLClient() as ml:
    response = ml.rest.search.post(tostring(body, encoding="unicode"))
    response.raise_for_status()

    computed_bucket works in both JSON and XML; its built-in anchor strings are separate from custom anchor elements.

    element_query_constraint and searchable_expression mirror deprecated native options. Prefer container_constraint and additional_query respectively; searchable_expression also requires MarkLogic's eval-search-string privilege.

    opt.control remains available for a native scalar name. opt.native accepts paired JSON members and XML elements for custom definitions. Prefer the typed constructors for standard options; use native components when an extension needs a shape specific to your server-side code.

    CTS queries¶

    CTS query constructors return concrete subclasses of CtsQuery, exported by mlclient.xquery like the structured vocabulary is by mlclient.search.structured: logical, selector, fragment and scope queries, word, value and range queries on text, elements, attributes, fields, JSON properties and paths, geospatial queries, temporal (period_compare_query, period_range_query, lsqt_query), timestamp (after_query, before_query) and registered queries. These objects retain the existing XQuery compilation behavior and also serialize independently to native CTS JSON or XML:

    from mlclient.xquery import cts

query = cts.and_query(
    [
        cts.collection_query("reports"),
        cts.word_query("blue", options=["lang=en", "unstemmed"]),
    ]
)
json_query = query.serialize()
xml_query = query.serialize("xml")
code, variables = query.compile()

    CTS JSON is not Search API structured JSON; its member names and representation follow native CTS serialization. CtsQuery additionally implements XqyExpression, so the same query also compiles to XQuery.

    Compile and execute CTS queries¶

    compile() returns XQuery source and bound variables without making a request. Pass the query to a CTS expression evaluated by ml.eval.expression(), or to CtsService.search() for hits with scores:

    from mlclient import MLClient
from mlclient.services import CtsService
from mlclient.xquery import cts

query = cts.and_query(
    [
        cts.collection_query("reports"),
        cts.word_query("blue"),
    ]
)
code, variables = query.compile()

with MLClient() as ml:
    documents = ml.eval.expression(cts.search(query=query))
    hits = CtsService(ml.rest).search(query=query)

    Each execution makes a separate request. Structured queries do not implement compile() and cannot be passed to XQuery evaluation or CtsService. See XQuery API for composing CTS under other functions.

    Local CTS serialization and limitations¶

    Local serialization describes the query you built, leaving database-dependent interpretation to MarkLogic. For example, when you omit lang=, the serialized query leaves the language unspecified so the destination database can supply its default. Options such as exact and query weights are also passed through for MarkLogic to interpret when it reads the query.

    For cts.near_query(), MLClient normalizes distances and minimum-distance options as MarkLogic's constructor does. Very large distances can still produce XML that cts:query rejects: the constructor can emit values above the signed 32-bit range accepted by the XML reader. Local serialization retains the constructor's representation, so such a query can fail when sent to the server.

    A serialized field query identifies its field by name. Run it against a database where that field is configured; the name alone is not enough to reconstruct the query in another database.

    Arbitrary expressions remain compilable, but local serialization rejects arguments that require server evaluation with TypeError. Arguments are serializable when they are literals or these builders:

    Argument Serializable forms
    QNames Unprefixed names ("title") and fn.qname(uri, name). A prefixed name such as "t:title" needs the compilation's namespace bindings, so use fn.qname.
    Range and JSON values Python literals: str, int, Decimal, float, bool, date, datetime (JSON property values support only strings, numbers and booleans).
    Regions cts.point(latitude, longitude), cts.box, cts.circle and cts.polygon of such points.
    Periods cts.period(start, end) with literal start and end.
    Range references Element, element-attribute, field, JSON-property and path references with an explicit type= option; URI, collection and IRI references. String collations must match the destination index.
    Region references cts.geospatial_region_path_reference with an explicit coordinate-system= option. Precision, units and invalid-value settings are retained.
    RDF values Atomic literals and FunctionCall("sem:iri", (uri,)). Other semantic-value constructors require evaluation.
    Model nodes Python dict, Element or ElementTree, including sequences of them. Literal xdmp.unquote(source) is also supported.

    Atomic value arguments must be ready-to-use Python literals. Local serialization preserves their types, including xsi:type in range-query XML and datatype attributes for RDF literals. It does not evaluate function calls in these values, including xs.* casts represented as FunctionCall and cts.uris(): to_json(), to_xml() and to_combined_query() raise TypeError. Such queries still compile to XQuery and can be evaluated explicitly on the server. Use 1 instead of xs.integer(1.9), or date(2026, 1, 1) instead of xs.date("2026-01-01"), when the result is already known and local serialization is needed. An xs.* builder may return a literal directly when its input already has the requested type (for example, xs.double(1.5)); that literal remains serializable. QName, region and other explicitly supported builders listed above retain their specialized serialization rules.

    Path expressions are serialized as written. MarkLogic resolves their prefixes where it reads the query, so prefer unprefixed paths or prefixes configured as database path namespaces. MarkLogic cannot read a namespaced document_root_query QName back from XML, even from its own constructor output; use the JSON form for that query. Conversely, MarkLogic cannot read an element-attribute reference back from its own JSON form, so to_json() raises TypeError for it and ml.search, which sends JSON, cannot run it; use to_xml() or run the query through eval.

    All 54 query constructors return concrete CtsQuery subclasses, including range_query, geospatial_region_query, column_range_query, triple_range_query, reverse_query and similar_query. Pass a serializable CTS query to ml.search to run it without evaluating XQuery. cts.parse() and cts.query() instead return RuntimeQuery: their concrete native query depends on server evaluation. They compose and compile normally, but local JSON/XML serialization raises TypeError, including when nested in another query. Evaluate them explicitly with ml.eval.expression() when needed. Reference namespace maps have no native serialized representation; use EQNames in reference paths or destination database path namespaces instead.

    Column range queries¶

    column_range_query can be serialized locally when you supply its TDE column ID with with_column_id(). Use an ID already stored in your application's configuration for the destination database and column:

    from mlclient.xquery import cts

# Example configured ID; use the ID for your destination's reports.items.price.
column_id = 11548423394257569743
query = cts.column_range_query("reports", "items", "price", 2)
query = query.with_column_id(column_id)
native_json = query.to_json()
native_xml = query.to_xml()

    This is a limitation of native CTS serialization: MarkLogic represents the column query as a triple-range-query whose predicate includes columnID. Schema, view and column names alone are insufficient to reconstruct that query from JSON/XML. Without the ID, local serialization raises TypeError. Compilation still uses the names and requires no ID; the library never fetches metadata implicitly.

    If the ID is not already known, obtain it from the server. The documented sql:columnID function avoids extracting it from a query's XML. An explicit eval request can return it as a Python integer:

    from mlclient import MLClient
from mlclient.xquery import cts

with MLClient() as ml:
    # Requires the reports.items view and its indexed price column.
    column_id = ml.eval.xquery(
        'sql:columnID("reports", "items", "price") => xs:integer()'
    )
    query = cts.column_range_query("reports", "items", "price", 2)
    query = query.with_column_id(column_id)
    native_json = query.to_json()
    native_xml = query.to_xml()

    This adds a server request before serialization. For a one-off search, it is usually simpler to execute the column query directly through CtsService or ml.eval.expression() (using an unfiltered cts.search or cts.uris) and let MarkLogic resolve the column. Explicit IDs remain available when you need to build or reuse a serialized REST query.

    Similar queries¶

    cts.similar_query() finds documents similar to a supplied example document. That example is the query's model document.

    For a JSON model document, serialize the query as JSON. On the tested versions, reading the query back from XML turns its JSON model into text. The query may still be accepted, but its input no longer has the original JSON type. This also happens with XML produced by MarkLogic itself.

    from mlclient.xquery import cts

model = {
    "title": "Coffee brewing",
    "text": "Freshly ground coffee beans",
}
query = cts.similar_query(model)
native_json = query.to_json()  # Preserves the model as a JSON object.

    The Python dictionary supplies the model directly. Building and serializing the query sends no request; no xdmp.unquote() wrapper is needed. query.to_xml() produces the native XML shape, but cannot prevent MarkLogic from reading the embedded JSON model as text.

    Choose the execution route according to the model:

    Model document Recommended route
    Literal JSON to_json() or ml.search, which sends JSON.
    Literal XML Either to_json() or to_xml() preserves the model.
    An expression such as fn.doc("/example.json") Execute through ml.eval.expression() or CtsService; local serialization raises TypeError.

    Direct execution through eval or CtsService also avoids the XML round-trip for a JSON model. We have no verified workaround that preserves a JSON model when the query is sent as XML.

    Similarity options are a separate concern. Pass a Python XML Element in the cts:distinctive-terms namespace:

    from xml.etree.ElementTree import fromstring

options = fromstring(
    '<options xmlns="cts:distinctive-terms"><max-terms>20</max-terms></options>'
)
query = cts.similar_query(model, options=options)

    Local JSON serialization supports score, max-terms, min-val, min-weight and complete. Unrecognized literal options raise ValueError; options that must be fetched or computed on the server require explicit evaluation.

    XML models and preservation limits¶

    For an XML model, pass an Element or an ElementTree directly:

    from xml.etree.ElementTree import ElementTree, fromstring
from mlclient.xquery import cts

root = fromstring("<article><title>Coffee brewing</title></article>")
query = cts.similar_query(root)  # An XML element as the model.
document_query = cts.similar_query(ElementTree(root))  # An XML document instead.
native_xml = query.to_xml()

    Serialization preserves the supplied XML content and namespace URIs. Python's XML parser may already have dropped comments or processing instructions; mlclient cannot restore them. Namespace prefixes may change during Python XML conversion. The element's tail (text after its closing tag) is outside the supplied node and is omitted.

    If you already have literal XML text, xdmp.unquote(source) remains available. For this form, local CTS serialization also retains comments, processing instructions and namespace declarations present in the text. Two special cases require care:

    • XML with a DTD: local serialization raises TypeError. Execute the query through ml.eval.expression() or CtsService so MarkLogic parses the document.
    • Literal XML using prefixes such as ns0: JSON serialization works, but XML serialization raises TypeError because ElementTree reserves those prefixes. Use another prefix or execute the query directly. This restriction does not apply to Python XML nodes: their generated prefixes are converted automatically.
